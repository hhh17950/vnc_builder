# VNC 自动化测试调度系统交接文档

> 更新日期：2026-10-16。本文以三个仓库当前本地提交为准，记录已经确认的需求、实际实现和内网接入工作。项目名称中的 `schdule` 是现有约定，调用、部署时保持原拼写。

## 1. 目标与范围

在多台物理机上部署 Worker。每台机器用**同一个 Linux 账号**运行 1～4 个 TurboVNC 桌面，每个桌面对应一个 Slot；同类 Worker 共享 Redis Stream，每个健康且空闲的 Slot 同时只执行一个 Squish 等 GUI 测试任务。API 负责任务持久化、调度授权、状态查询和取消。

当前版本以 CentOS 7、TurboVNC 3.0.1、GNOME 为内网接入目标。应用数据、桌面内容、缓存和文件的完整基线恢复不在当前范围。任务脚本负责启动 Squish Server、Runner 和被测应用，并自行管理不同 Slot 的 Squish 端口。

### 已确认的需求

| 主题 | 当前约定 |
| --- | --- |
| 部署 | `vnc_schdule_api`、`vnc_worker`、`vnc_builder` 为三个独立 Git 仓库；每台物理机运行一个 Worker。 |
| 账号与桌面 | 单账号运行 1～4 个 TurboVNC 桌面，默认目标 DISPLAY 为 `:1`～`:4`。Worker、VNC 脚本和任务均使用当前账号，不在运行过程中使用 `su`。 |
| 创建桌面 | Worker 启动时调用 `vnc_manager.sh create -n N`。脚本跳过已有桌面，只补齐缺失的桌面。空闲桌面由独立周期检查并恢复；领任务时不重新创建桌面。 |
| 领任务 | Slot 必须同时空闲、VNC 进程存在、`xset q` 可连接，才从共同的 Stream Consumer Group 取消息；启动任务前还须取得 API 授权。 |
| 任务参数 | 请求包含 `command` 参数数组和物理机上的**绝对** `cwd`；Worker 直接在该目录执行。不再配置 `VNC_SHARED_ROOT`。 |
| 超时与取消 | 默认任务期限 7200 秒，从 API 授权时开始，排队时间不计入。取消请求先落库，经心跳响应持续下发，Worker 确认清理后才回报终态。 |
| 日志 | 服务日志按天和 100 MB 分片，压缩并保留 30 天。任务 stdout、stderr 分别写入任务 `cwd/job_log/` 下带日期时间的文件，不做分片。 |
| 创建接口 | 每次 POST 创建新任务，不使用 `Idempotency-Key`；Stream 消息可能重复，数据库执行授权负责阻止重复启动。 |
| 安全边界 | Worker 内部 API 当前无 Token 鉴权，按可信内网部署；数据库密码只经部署环境提供。 |

## 3. 已实现的运行流程

1. 客户端创建任务。API 在同一 PostgreSQL 事务中写入 `tasks` 和 `outbox_events`，返回 `queued`；超时值在创建时写入任务。
2. API 后台循环投递 Outbox 到 Redis Stream。消息携带 `task_id`、`event_id`、`generation`、`version=1`；任务参数以数据库为准。投递失败按退避重试。
3. Worker 启动时验证当前账号、补齐 VNC 桌面、解析脚本 `list` 返回的 JSON、执行 `xset q`，然后注册 `worker_id`、本次启动的 `session_id` 和 Slot 列表。
4. 每个健康空闲 Slot 从同一个 Consumer Group 取一条消息，调用 API `claim`。数据库在一个事务里把任务置为 `running`，并写入 `worker_id/session_id/slot_id/started_at/deadline_at`。重复消息不能取得第二个执行资格。
5. Worker 给该任务单独设置 `DISPLAY`，在请求的 `cwd` 运行 `command`。任务使用独立进程组；stdout 和 stderr 持续落盘。
6. 心跳独立运行，续租并接收待处理的取消任务 ID。取消、超时及正常完成都清理任务进程组：先发 SIGTERM，期限后发 SIGKILL，随后检查进程和 VNC 健康。
7. Worker 先将结果回报 API、写入 PostgreSQL，再 ACK Redis 消息。ACK 失败允许重复处理，结果回调按任务终态幂等。
8. Worker 正常停止时清理任务并携带 `session_id` 注销。失联期间 API 不改任务状态，等待最终态；`deadline + 60s` 仍无结果则兜底标 `timed_out`。人工注销或新 session 接管时，未确认执行标为 `unknown`。

### 数据和状态

PostgreSQL 是任务和 Worker 租约的权威存储；Redis 只提供消息通知。主要表为 `tasks`、`outbox_events`、`workers`。数据库时间使用 UTC；Worker 的 claim 响应使用 Unix 秒时间戳，任务对外时间字段仍为 ISO 日期时间。

任务状态：`queued` → `running` → `succeeded` / `failed`；取消经过 `cancel_requested` → `cancelled`；超时经过 `timeout_requested` → `timed_out`。人工注销或新 session 接管时使用 `unknown`（结果未知）。Slot 还维护 `idle`、`reserved`、`running`、`cleaning`、`reporting`、`recovering`、`error` 等本地状态。清理未确认的 Slot 不再领任务，也不会被普通桌面恢复循环直接解除隔离。

API 的对账循环处理失联租约、到期 attempt、长期未授权的 queued 任务和 Redis pending 消息。已获得执行授权的任务不会因为消息丢失直接重跑。当前实现没有 Redis Stream 的自动裁剪，长期运行时需监控容量，并在确认 pending 安全后设计保留策略。

## 4. HTTP 接口

| 方法与路径 | 用途 |
| --- | --- |
| `POST /api/v1/tasks` | 创建任务；请求主体含 `command`、绝对 `cwd`，可选 `timeout_seconds`。 |
| `GET /api/v1/tasks/{task_id}` | 查询任务详情，含 `job_info`（日志路径与上传后的文件 id）。 |
| `GET /api/v1/tasks?limit=50&offset=0` | 分页查询。 |
| `POST /api/v1/tasks/{task_id}/cancel` | 接受取消请求，返回 HTTP 202；执行中任务需等待 Worker 清理。 |
| `GET /api/v1/workers` | 查看 Worker 在线状态及 Slot 快照。 |
| `POST /api/v1/workers/register` | Worker 注册，返回租约秒数。 |
| `POST /api/v1/workers/{worker_id}/heartbeat` | 续租并返回 `cancel_task_ids`。 |
| `POST /api/v1/workers/{worker_id}/claim` | 授予任务执行资格。 |
| `POST /api/v1/workers/{worker_id}/tasks/{task_id}/result` | 持久化执行结果。 |
| `POST /api/v1/workers/{worker_id}/shutdown` | 当前 Session 正常注销。 |
| `POST /api/v1/workers/{worker_id}/unregister` | 人工强制下线；先确认旧进程已停止。 |

示例：

```bash
curl -X POST http://<api-host>:8088/api/v1/tasks \
  -H 'Content-Type: application/json' \
  -d '{"command":["./run_case.sh","case-001"],"cwd":"/home/user/cases","timeout_seconds":7200}'
```

`command` 不经过 Shell 展开。若需要管道、重定向等功能，请在任务脚本中实现。不同物理机共用队列时，每台机器必须能访问任务指定的同一绝对路径及所需输入文件。API 只回报任务状态，不回传日志路径；任务 stdout/stderr 由 Worker 写入任务 `cwd/job_log/`。

## 5. VNC 与防锁屏

Builder 的生产脚本提供 `create [-n 1-4]`、`list`、`stop [:1-:4]`、`help`；单账号操作，不启动或管理 Xorg `:0`、VirtualGL 和 Squish。`list` 的 stdout 为 `user/group/display/state` JSON 数组，便于 Worker 解析；可视化清单写到 stderr。Worker 从实际 `display` 取 Slot 编号，不假定用户名映射 DISPLAY。

防锁屏属于桌面预置：`xstartup.example` 配置 `xset s off`、`xset s noblank`、`xset -dpms`，GNOME 的锁屏及空闲策略另由 dconf/主机设置关闭。Worker 只做 `xset q` 连通性检查；它不能证明 GNOME 未锁屏。安装器不会覆盖 `~/.vnc/xstartup`。替换步骤见 `vnc_builder/GNOME部署说明.md`。

## 6. 配置与运行

### 关键配置

| API | 默认或要求 | Worker | 默认或要求 |

| `VNC_REDIS_URL` | Redis 地址 | `VNC_REDIS_URL` | 同一 Redis |
| `VNC_REDIS_PREFIX` | `vnc_schedule` | `VNC_REDIS_PREFIX` | 必须与 API 一致 |
| `VNC_TASK_TIMEOUT_SECONDS` | `7200` | `VNC_WORKER_ID` | 每台物理机唯一、稳定，部署时显式填写 |
| `VNC_LEASE_SECONDS` | `30` | `VNC_SLOT_COUNT` | 配置 1～4，代码默认 2 |
| `VNC_LOG_DIR` | `logs` | `VNC_MANAGER_SCRIPT` | 生产通常为 `/opt/scripts/vnc_manager.sh` |
|  |  | `VNC_HEARTBEAT_SECONDS` | `5` |
|  |  | `VNC_RECOVERY_INTERVAL_SECONDS` | `10` |
|  |  | `VNC_STOP_GRACE_SECONDS` / `VNC_CLEANUP_SECONDS` | `5` / `10` |

两服务的日志时区默认 `Asia/Shanghai`，服务日志保留 30 天。Worker 不配置账号，始终以运行它的 Linux 账号工作；builder 的 `VNC_DESKTOP_USER` 仅用于生成 systemd 服务的 `User=`。`.env` 由 Pydantic Settings 从**当前工作目录**读取；systemd 部署由 `EnvironmentFile=/etc/vnc-worker.env` 注入环境变量，服务工作目录是 `/opt/vnc_worker`。数据库密码不要写入交接文档、Git 或日志。

### 普通用户直接调试 Worker

1. 在同一账号终端确认 VNC 脚本能运行，并确认 `DISPLAY=:1 xset q` 成功。
2. 在 `vnc_worker/` 下复制 `.env.example` 为 `.env`，设置实际 API/Redis、唯一 `VNC_WORKER_ID`、脚本路径，并将 `VNC_LOG_DIR` 设为可写目录（例如 `./logs`）。
3. 从 `vnc_worker/` 目录运行：

   ```bash
   .venv/bin/python -m src.cli run
   ```

   PyCharm 使用模块 `src.cli`、参数 `run`，工作目录设为 `vnc_worker/`。打包后可在有相同配置的工作目录运行 `./dist/vnc_worker run`。不要同时用相同 `worker_id` 启动服务版和调试版。

### CentOS 7 安装

在兼容 CentOS 7 glibc、同 CPU 架构的 Linux 环境执行 `vnc_worker/scripts/build_executable.sh`，将 `dist/vnc_worker` 放进 `vnc_builder/dist/`。复制 `vnc_builder/vnc-worker.env.example` 为 `vnc-worker.env`，填入本机配置，再以管理员身份运行 `sudo bash install.sh install`。安装动作需要管理员权限，安装后的 `vnc-worker.service` 以配置的桌面账号运行。日常使用 `sudo bash install.sh status|start|stop|restart|logs|uninstall`。

Builder 安装到 `/opt/vnc_worker/vnc_worker`、`/opt/scripts/vnc_manager.sh`、`/etc/vnc-worker.env`，并生成 `vnc-worker.service`。更改桌面账号后应重新执行 install，以更新服务的 `User=`。原有 `vnc-worker.env` 在重复安装时保留。

API 先配置数据库，再执行 `alembic upgrade head`，之后启动 `uvicorn src.main:app`。开发 Compose 和详细命令见各仓库 README。API 迁移 `0004_drop_creation_key` 会删除旧幂等键字段；升级前先结束旧 Worker，旧相对 `cwd` 的排队任务应取消后用绝对路径重新创建。

## 7. 日志、结果和故障处理

- 服务日志：API 在自身 `VNC_LOG_DIR`，Worker 在自身 `VNC_LOG_DIR`；写入文件及终端/journal，按日和 100 MB 分片、gzip 压缩、保留 30 天。正常心跳不逐条记 INFO。
- 任务输出：写入任务 `cwd/job_log/` 下的 `stdout-YYYYmmdd-HHMMSS.log` 与 `stderr-YYYYmmdd-HHMMSS.log`，不做分片。Worker 回报两个路径，API 同步上传到 file_management 并写入 `job_info`；上传失败只留空 id、不影响任务终态。
- 注册 409：确认旧 Worker 已停止，再调用 `POST /api/v1/workers/{worker_id}/unregister`。强制注销将未完成执行记为 `unknown`，不会自动重跑。
- 正常 Ctrl+C、SIGTERM：Worker 停止领任务、清理当前任务并主动 shutdown。SIGKILL 或调试器强制杀进程无法执行 Python 的清理路径；重启前要检查并清理旧任务进程。
- 桌面异常：Worker 只恢复空闲且未发生任务进程清理失败的 Slot；正在执行的桌面不会被恢复循环停止。`error` Slot 不领任务。

任务进程清理以**进程组**为边界。任务脚本、Squish/AUT 子程序应以前台或同进程组方式运行；主动 `setsid`、daemonize 脱离进程组的程序不受此清理覆盖，需要脚本自行关闭。systemd 服务使用 `KillMode=control-group`，停止服务时会清理仍处于该服务 cgroup 的子进程；服务启动的 VNC 如果仍在其中，也可能随服务停止，下次启动会重新补齐。
